# LicenseManagement.Client — Code Audit Report

**Date:** 2026-05-14
**Branch:** `master` @ `f6e53048d2c27588af1f3f54cd141b225289f7b2`
**Auditor:** senior-dotnet multi-lens review
**Lenses applied:** clean-code, design-patterns, external-integrations-review
**Lenses skipped:** razor-best-practices, website-audit (no Razor or web-host code in this SDK)
**Scope:** 18 production `.cs` files, 1 test file, `.csproj` files

---

## Executive Summary

`LicenseManagement.Client` is a small, well-structured HTTP SDK targeting `netstandard2.0` and `net6.0+`. The shape of the code is sound — a single facade class, plain DTOs, an HMAC webhook validator, and a clean DI extension. There are no architectural problems.

However, the SDK has **three categories of risk that need attention before it can be considered production-grade**:

1. **Data-integrity holes in non-idempotent flows.** `ResetReceiptCodeAsync` voids a receipt before creating its replacement and has no rollback. None of the `Create*` methods accept an idempotency key, so any caller-side retry against a flaky network or a 5xx will silently duplicate licenses, receipts, and seat allocations.
2. **Webhook signature/timestamp validation has two latent bugs.** The timestamp is parsed as `DateTime` with `Kind=Unspecified` and then subtracted from `DateTime.UtcNow`, so a server timestamp expressed in local time is silently accepted. The constant-time comparison operates on hex strings rather than raw HMAC bytes, leaks length differences early, and does not use the framework's hardened `CryptographicOperations.FixedTimeEquals`.
3. **No observability, no retry guidance, no User-Agent.** Callers integrating this SDK have no signal about which endpoint failed, how slow it was, or which SDK version is in production.

Everything else (15 medium / 9 low findings) is hygiene: redundant null-forgiving `!` operators, magic numbers, mixed namespace styles, missing `ConfigureAwait(false)`, and one minor inconsistency between XML docs and runtime behavior on 404s.

The top five fixes are listed at the end of this document.

## CRITICAL

### C-1. `ResetReceiptCodeAsync` is non-atomic and corrupts data on partial failure

**File:** `LicenseManagement.Client/LicenseManagementClient.cs:131-173`

The method sequence is:

1. Void the existing receipt by patching `Qty=0` and `Expires=DateTimeOffset.UtcNow`.
2. Generate a new receipt code via `GET /receipts/generate-code`.
3. Create a brand-new receipt with the new code.

If step 2 or 3 throws — transient network error, 429 throttling, server 5xx, cancellation — the original receipt is permanently voided with no compensation. The customer loses the seats and has no recovery path from the SDK side.

**Impact:** Data loss for end customers. Recovery requires manual server-side intervention.

**Recommended fix (in order of preference):**

- **Best:** Add a single server-side endpoint `POST /receipts/{id}/rotate-code` that performs the void+create transactionally and returns the new receipt. Replace `ResetReceiptCodeAsync` with a call to it.
- **Acceptable:** Wrap the three-step flow in a try/catch that, on failure of step 2 or 3, attempts to restore the original `Qty` and `Expires` via a compensating PATCH. Surface both errors in `LicenseManagementException`.
- **Minimum:** Document the failure mode clearly in the XML doc comment and surface a typed `ReceiptResetException` so callers can distinguish "void succeeded, create failed" from "everything failed".

### C-2. No idempotency keys on any Create operation

**File:** `LicenseManagement.Client/LicenseManagementClient.cs:59-72, 95-108, 204-217, 233-246, 298-302`

The following methods POST without an `Idempotency-Key` header:

- `CreateLicenseAsync`
- `CreateReceiptAsync`
- `CreateProductAsync`
- `RegisterComputerAsync`
- `CreateWebhookAsync`

A timeout-then-retry by the caller (or by a Polly policy added via `configureBuilder` in DI registration) will produce duplicates. Duplicate receipts mean duplicate seat allocations and duplicate billing impact.

**Recommended fix:**

Add an optional `string? idempotencyKey = null` parameter to each `Create*` method (and corresponding interface signature). When non-null, attach as a request header:

```csharp
using var request = new HttpRequestMessage(HttpMethod.Post, "licenses")
{
    Content = JsonContent.Create(body, options: JsonOptions)
};
if (idempotencyKey is not null)
    request.Headers.Add("Idempotency-Key", idempotencyKey);
using var response = await _httpClient.SendAsync(request, ct).ConfigureAwait(false);
```

Document that callers should generate a deterministic key per logical create (e.g. a UUID stored alongside the operation in their own database) so a retry uses the same key.

### C-3. Webhook timestamp validation accepts ambiguous local-time strings

**File:** `LicenseManagement.Client/Webhooks/WebhookSignatureValidator.cs:107,113`

```csharp
if (!DateTime.TryParse(timestampString, null, DateTimeStyles.RoundtripKind, out var timestamp))
    return false;

var diff = DateTime.UtcNow - timestamp;
```

If the server emits a timestamp without an explicit offset (e.g. `2026-05-14T10:30:00`), `DateTime.TryParse` returns `Kind=Unspecified`. The subtraction at line 113 then treats it as if it were UTC, so a local-time string from a server in a different time zone is silently accepted within the tolerance window — defeating replay protection.

**Recommended fix:**

```csharp
if (!DateTimeOffset.TryParse(
        timestampString,
        CultureInfo.InvariantCulture,
        DateTimeStyles.AssumeUniversal | DateTimeStyles.RoundtripKind,
        out var timestamp))
    return false;

var diff = DateTimeOffset.UtcNow - timestamp;
if (diff.Duration() > tolerance)
    return false;
```

Better still, match Stripe / GitHub convention and send a Unix-seconds integer (`long.TryParse` → `DateTimeOffset.FromUnixTimeSeconds`). Unambiguous, locale-independent, byte-cheap.

## HIGH

### H-1. `ConstantTimeEquals` operates on hex strings, not bytes

**File:** `LicenseManagement.Client/Webhooks/WebhookSignatureValidator.cs:121-135`

```csharp
private static bool ConstantTimeEquals(string a, string b)
{
    if (a.Length != b.Length) return false; // early return leaks length
    var diff = 0;
    for (var i = 0; i < a.Length; i++)
        diff |= a[i] ^ b[i];
    return diff == 0;
}
```

Two issues:

1. The early length-check leaks length difference. For HMAC-SHA256 hex output (always 64 chars), this is harmless in practice, but it sets a bad precedent.
2. Iterating over hex chars doubles the work versus comparing the raw HMAC bytes, and on some runtimes the XOR over `char` can have a subtle timing wobble that the framework's hardened comparator avoids.

**Recommended fix:**

On `net6.0+`, use `CryptographicOperations.FixedTimeEquals` over the raw HMAC bytes:

```csharp
using var hmac = new HMACSHA256(Encoding.UTF8.GetBytes(secret));
var computed = hmac.ComputeHash(Encoding.UTF8.GetBytes(payload));
var provided = Convert.FromHexString(signatureHeader); // net5+
return CryptographicOperations.FixedTimeEquals(computed, provided);
```

For `netstandard2.0`, keep the manual byte-array comparison (still no early return), parsing the hex via a small `HexToBytes` helper.

### H-2. `EnsureSuccessAsync` ignores cancellation

**File:** `LicenseManagement.Client/LicenseManagementClient.cs:457-471`

```csharp
private static async Task EnsureSuccessAsync(HttpResponseMessage response)
{
    if (response.IsSuccessStatusCode) return;
    var body = await response.Content.ReadAsStringAsync().ConfigureAwait(false); // <- no token
    ...
}
```

Two related problems:

1. The method takes no `CancellationToken`. On a slow / hanging error response, the body read cannot be cancelled.
2. On `net6.0+`, `HttpContent.ReadAsStringAsync(CancellationToken)` exists; on `netstandard2.0` it does not, so the cancellation will be best-effort there.

**Recommended fix:**

```csharp
private static async Task EnsureSuccessAsync(HttpResponseMessage response, CancellationToken ct)
{
    if (response.IsSuccessStatusCode) return;
#if NET6_0_OR_GREATER
    var body = await response.Content.ReadAsStringAsync(ct).ConfigureAwait(false);
#else
    var body = await response.Content.ReadAsStringAsync().ConfigureAwait(false);
#endif
    ...
}
```

Thread the token through from every call site.

### H-3. Error messages drop URL and HTTP method

**File:** `LicenseManagement.Client/LicenseManagementClient.cs:462-471`

The status-to-message mapping (`404` → `"Resource not found"`, etc.) hides the endpoint that failed. The body is preserved in `LicenseManagementException.ResponseContent`, but only the `Message` is captured by default logging configurations.

**Recommended fix:**

Include method and URL:

```csharp
var message = response.StatusCode switch
{
    HttpStatusCode.NotFound => $"Resource not found at {response.RequestMessage?.Method} {response.RequestMessage?.RequestUri}",
    HttpStatusCode.Unauthorized => $"Authentication failed for {response.RequestMessage?.RequestUri}",
    ...
};
```

### H-4. 14 null-forgiving `!` unwraps on JSON deserialization

**Files / lines:** `LicenseManagement.Client/LicenseManagementClient.cs:69, 72, 105, 108, 214, 217, 243, 246, 302, 331, 375, 383, 391, 399`

Every `Create*` and several `Get*` calls do `(await response.Content.ReadFromJsonAsync<T>(...))!`. If the server returns the literal `null`, or a 204 with no body slips through somehow, the call site throws `NullReferenceException` with no context.

**Recommended fix:**

Replace each `!` with an explicit guard:

```csharp
var result = await response.Content.ReadFromJsonAsync<License>(JsonOptions, ct).ConfigureAwait(false)
    ?? throw new LicenseManagementException(
        $"Server returned an empty body for {response.RequestMessage?.Method} {response.RequestMessage?.RequestUri}",
        response.StatusCode,
        responseContent: null);
return result;
```

### H-5. Webhook filter has no body-size guard

**File:** `LicenseManagement.Client/Filters/EnsureIsFromLicenseManagementAttribute.cs:60, 82-86`

`request.EnableBuffering()` is called without size limits, then the body is read by a `StreamReader`. A malicious client can POST a multi-GB body and exhaust server memory (or disk, once buffering spills to a temp file) **before** the signature check rejects it.

**Recommended fix:**

```csharp
const int MaxWebhookBodyBytes = 1 * 1024 * 1024; // 1 MB
if (request.ContentLength is > MaxWebhookBodyBytes)
{
    context.Result = new StatusCodeResult(StatusCodes.Status413PayloadTooLarge);
    return;
}
request.EnableBuffering(bufferThreshold: 81920, bufferLimit: MaxWebhookBodyBytes);
```

Make the limit configurable on `WebhookOptions`.

### H-6. Test project targets `net10.0` (preview)

**File:** `Tests/LicenseManagement.Client.Tests/LicenseManagement.Client.Tests.csproj:4`

`net10.0` is an unreleased / preview framework as of the date of this audit. CI runners with stock .NET SDKs and most contributor machines will fail `dotnet restore`.

**Recommended fix:** Pin to `net8.0` (matches the library's max TFM) or `net9.0` until net10 GA.

## MEDIUM

### M-1. `HttpClient` is mutated inside the constructor

**File:** `LicenseManagement.Client/LicenseManagementClient.cs:39-46`

The constructor calls `ConfigureHttpClient()`, which sets `BaseAddress`, `Timeout`, calls `DefaultRequestHeaders.Clear()`, and adds `Accept` and `Authorization` headers. Because `LicenseManagementClient` is registered via `services.AddHttpClient<LicenseManagementClient>(...)`, the `HttpClient` instance comes from `IHttpClientFactory` and may be configured by callers via the `configureClient` parameter or shared with other consumers in pathological cases.

The `DefaultRequestHeaders.Clear()` call is especially fragile — it wipes any headers a caller added through `AddHttpClient<>().ConfigureHttpClient(...)`.

**Recommended fix:** Move all HttpClient configuration into the DI registration in `ServiceCollectionExtensions.cs`:

```csharp
services.AddHttpClient<LicenseManagementClient>((sp, http) =>
{
    var opts = sp.GetRequiredService<IOptions<LicenseManagementClientOptions>>().Value;
    http.BaseAddress = new Uri(opts.BaseUrl);
    http.Timeout = opts.Timeout;
    http.DefaultRequestHeaders.Accept.Add(new MediaTypeWithQualityHeaderValue("application/json"));
    http.DefaultRequestHeaders.Authorization = new AuthenticationHeaderValue("Bearer", opts.ApiKey);
    http.DefaultRequestHeaders.UserAgent.ParseAdd($"LicenseManagement.Client/{AssemblyVersion}");
});
```

The constructor then only stores the injected `HttpClient`.

### M-2. Public classes are not `sealed`

**Files:** all of `Models/*.cs`, `Requests/*.cs`, `Exceptions/LicenseManagementException.cs`, `Options/*.cs`, `LicenseManagementClient.cs`.

No explicit inheritance intent. Convention for published SDKs: `sealed` unless extensibility is part of the contract. Most consequential for `LicenseManagementClient` (subclasses would inherit the constructor side effects from M-1).

**Recommended fix:** Add `sealed` to all concrete classes.

### M-3. `LicenseManagementClient` is 477 lines spanning six resource families

**File:** `LicenseManagement.Client/LicenseManagementClient.cs`

The file mixes Licenses, Receipts, Products, Computers, SigningKeys, and Webhooks. The clean-code skill flags classes >300 lines.

**Recommendation:** **Do not split immediately** — the facade pattern is correct for an SDK, and one consumer per resource family is fine. But if a second internal consumer emerges (CLI, admin tool, etc.), split into partials:

- `LicenseManagementClient.Licenses.cs`
- `LicenseManagementClient.Receipts.cs`
- `LicenseManagementClient.Products.cs`
- `LicenseManagementClient.Computers.cs`
- `LicenseManagementClient.SigningKeys.cs`
- `LicenseManagementClient.Webhooks.cs`

…with shared helpers (`EnsureSuccessAsync`, `ReadJsonOrDefaultAsync`, `PatchAsJsonAsync`) moved to `Internal/HttpHelpers.cs`.

### M-4. Create-and-follow-Location pattern duplicated 4 times

**Files / lines:** `LicenseManagementClient.cs:65-72, 101-108, 210-217, 239-246`

Each `Create*` method:

1. POSTs the request.
2. Calls `EnsureSuccessAsync`.
3. Reads the `Location` header.
4. Issues a GET to fetch the freshly-created resource.
5. Force-unwraps the result with `!`.

**Recommended fix:** Extract a helper:

```csharp
private async Task<T> CreateAndFetchAsync<T>(
    string path,
    object body,
    CancellationToken ct,
    string? idempotencyKey = null)
{
    using var request = new HttpRequestMessage(HttpMethod.Post, path)
    {
        Content = JsonContent.Create(body, options: JsonOptions)
    };
    if (idempotencyKey is not null)
        request.Headers.Add("Idempotency-Key", idempotencyKey);

    using var response = await _httpClient.SendAsync(request, ct).ConfigureAwait(false);
    await EnsureSuccessAsync(response, ct).ConfigureAwait(false);

    var location = response.Headers.Location?.ToString()
        ?? throw new LicenseManagementException(
            "Server did not return a Location header on resource creation",
            response.StatusCode, null);

    var fetched = await _httpClient.GetFromJsonAsync<T>(location, JsonOptions, ct).ConfigureAwait(false);
    return fetched ?? throw new LicenseManagementException(
        $"Server returned empty body for GET {location}",
        HttpStatusCode.OK, null);
}
```

Saves ~30 lines and fixes H-4 simultaneously.

### M-5. No `ILogger` injection, no observability

**File:** `LicenseManagementClient.cs` (whole file)

There is no logging anywhere. Production consumers cannot diagnose slow / failing calls without wrapping the SDK themselves.

**Recommended fix:** Inject `ILogger<LicenseManagementClient>?` (nullable, so it's optional) and log at the appropriate level on failures. Better still, register a typed `DelegatingHandler` via `AddHttpMessageHandler<LicenseManagementClientLoggingHandler>()` so logging composes with caller-supplied Polly policies.

### M-6. No retry / circuit-breaker guidance for callers

**File:** `LicenseManagement.Client/Extensions/ServiceCollectionExtensions.cs`

The DI extension accepts `Action<IHttpClientBuilder>? configureBuilder` (good) but does not document or recommend a default Polly policy for idempotent reads, 429 responses, or transient 5xx.

**Recommended fix:** Add an `AddDefaultResiliencePolicies()` extension that callers can opt into, OR document the recommended Polly setup in the public XML docs / README.

### M-7. Manual `Uri.EscapeDataString` on every URL build

**Files / lines:** `LicenseManagementClient.cs:53, 89, 121, 178, 190, 227, 252, 264, 344-348`

Every method does `$"resource?key={Uri.EscapeDataString(value)}"` by hand. Easy to forget a future parameter.

**Recommended fix:** Small internal `UrlBuilder` static helper, or extension on `string`.

### M-8. 404-handling inconsistent with XML docs

**Files:**
- `LicenseManagement.Client/Interfaces/ILicenseManagementClient.cs:19, 46, 101, 128` — XML docs claim `Get*` methods return `null` on 404.
- `LicenseManagement.Client/LicenseManagementClient.cs:51-56, 87-92, 188-193, 225-230` — implementations call `EnsureSuccessAsync`, which throws on 404.
- `LicenseManagement.Client/LicenseManagementClient.cs:286-295, 356-365` — `GetWebhookAsync` and `GetWebhookDeliveryAsync` correctly short-circuit 404 to `null`.

**Recommended fix:** Pick one contract. Either make all `Get*By*` methods return `null` on 404 (matches the XML docs), or fix the XML docs to say "throws `LicenseManagementException` on 404". Consistency matters more than which choice you make.

### M-9. Webhook body buffering has no limit

See H-5; documenting the underlying `EnableBuffering()` call independently because it is the root cause.

### M-10. `WebhookOptions.TimestampTolerance` is unvalidated

**File:** `LicenseManagement.Client/Options/WebhookOptions.cs:30`

A misconfigured `TimeSpan.Zero` would reject every request. A negative span is undefined.

**Recommended fix:** Implement `IValidateOptions<WebhookOptions>` and require `TimestampTolerance > TimeSpan.Zero && < TimeSpan.FromHours(1)`.

## Design-pattern opportunities (advisory)

Concrete reuse targets — apply these:

- **`CreateAndFetchAsync<T>` helper** (M-4). Four-way duplication, clear shape, simultaneously fixes H-4 (null-forgiving) and C-2 (idempotency).
- **`EnsureSuccessAsync` / `ReadJsonOrDefaultAsync` → static helpers** (M-3). They are already shape-correct; just relocate to `Internal/HttpHelpers.cs` if the main file is split.

Patterns NOT to apply yet (clean-code rule: no abstraction without a second use case):

- **Per-resource interfaces** (`ILicenseService`, `IReceiptService`). No second consumer exists. Single facade is correct.
- **`Result<T>` railway type.** Existing exception-based flow is idiomatic for an HTTP SDK and matches `HttpClient` itself.
- **Generic `IHttpRepository<T>`**. Over-engineering for six resources with materially different shapes.

## Top 5 Fixes by Impact

In priority order:

1. **Fix `ResetReceiptCodeAsync` atomicity (C-1).** Highest data-corruption risk in the library. Either move to a server-side single endpoint or add compensating rollback. Nothing else on this list matters as much.

2. **Fix the two webhook security bugs together (C-3 + H-1).** Switch timestamp parsing to `DateTimeOffset` with `AssumeUniversal`, and switch byte comparison to `CryptographicOperations.FixedTimeEquals` over the raw HMAC bytes. These are the only two security-grade defects in the codebase; a webhook validator with either bug is broken regardless of the other 25 findings.

3. **Add idempotency-key support to all `Create*` calls (C-2)** with documented retry guidance (M-6). Combined, these turn the SDK from "fine on the happy path" into "production-safe under flaky networks". Implement as part of the `CreateAndFetchAsync<T>` extraction (M-4).

4. **Stop force-unwrapping create responses (H-4) and align 404-handling across single-resource GETs (M-8).** Pick one contract — throwing or nullable — and make the XML docs and code agree. Throwing `LicenseManagementException` with an explicit message is the lower-risk path.

5. **Move `HttpClient` configuration out of the constructor and into the `AddHttpClient<>` registration (M-1).** Bundle the User-Agent header (L-3) and observability hooks (M-5) into the same refactor — one PR fixes three findings and aligns the SDK with `IHttpClientFactory` conventions.
